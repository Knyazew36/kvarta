     Инструкции и гостевой доступ: перевод на API

     Context

     Вкладка «Инструкции» объекта, вкладка «Инструкции» брони и четыре гостевые
     страницы — статичные моки. На бэке (../api-rentybot) готовы 16 ручек тега
     Instructions (кабинет) и 7 ручек GuestAccess (гость), orval-функции уже
     сгенерированы (src/shared/api/generated/instructions, .../guest-access).
     Хуков, ключей, схем и экранов под них нет.

     Решено: делаем всё сразу (кабинет + гость); предпросмотр «Глазами гостя»
     уезжает с объекта на бронь; чего нет на бэке — MOCK_BORDER (красный),
     работает на API, но не как в макете — DeviationNote / DEVIATION_BORDER
     (жёлтый, src/shared/mock/).

     Что важно знать про бэк (проверено по коду)

     - Инструкции: максимум 5, по одной на тип (route | rules | wifi | access | 
       checkout), удаления нет — только enabled=false. Список отдаёт метаданные
       без текста и без даты изменения. Текст (GET :id) и предпросмотр — только
       owner/manager; administrator видит список/историю, на текст 403.
     - wifi/access всегда sensitive=true; sensitive:false для них → 422. type
       неизменяем. Повтор типа → 409 instruction_exists.
     - Update: version + хотя бы одно поле; каждый успешный POST = новая версия,
       даже без изменений → шлём только dirty-поля, без изменений запрос не
       шлём.
     - Policy: до настройки version=0. Поля: opening_offset_minutes (±10080),
       requires_ready. requires_payment_approval всегда true,
       sensitive_delivery_available всегда false — чувствительные инструкции
       гостю сейчас не выдаются вообще (sensitive_delivery_unavailable в
       InstructionService::conditions). Обычные открыты активному гостю до
       выезда, окно/оплата/готовность на них не влияют.
     - Все мутации на архивном объекте → 409 property_archived; чтение работает.
     - Приглашение гостя: token приходит только в ответе создания, доставки нет
       — ссылку строит фронт. Новое приглашение на тот же email отзывает
       прежние. Действия с grant (confirm / revoke / approve-payment) и отзыв
       приглашения требуют version + reason.
     - Смена дат брони сбрасывает разрешение оплаты, отмена — отзывает гранты
       (GuestAccessService::bookingChanged) → мутации брони должны
       инвалидировать гостевой доступ.
     - Гость: GET guest/bookings/:id/instructions/:id пишет opened_at;
       acknowledge требует, чтобы версию сначала открыли (иначе 409
       instruction_not_opened). Закрыто → 409 instruction_locked +
       locked_reasons. Текст не кешировать и не класть в localStorage.
     - Истории (instruction_events) — 20/стр., id ASC; metadata без текстов;
       actor_id → имена через useTeamMembers (только owner/manager, как в
       BookingHistoryTab).
